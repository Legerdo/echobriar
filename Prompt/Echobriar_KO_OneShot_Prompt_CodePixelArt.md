# 목표

브라우저에서 실행되는 완성형 2D 픽셀아트 반응형 턴제 RPG **《에코브라이어: 잔향의 뿌리》**를 실제로 구현하라.

기획서, 목업, 전투 데모, 기술 시연, TODO 목록만 만들고 끝내지 않는다. 타이틀 화면에서 시작해 탐험, 파티 성장, 일반 전투, 세 개의 성소, 세 수호자, 최종 보스, 엔딩과 승리 화면까지 정상적으로 플레이 가능한 하나의 게임을 완성한다.

게임의 기본 언어는 한국어(`ko-KR`)다. 외부 설명 없이 처음 실행한 사용자가 조작법과 목표를 이해하고 끝까지 플레이할 수 있어야 한다.

핵심 목표는 다음 한 문장으로 정의한다.

> **턴제 전략과 실시간 반응 입력이 서로 분리된 시스템이 아니라 하나의 전투 자원 경제로 연결되는 2D RPG를 만든다.**

# 1. 완성 기준

첫 클리어 목표 시간은 약 **30~60분**이다. 분량을 억지로 늘리는 반복 전투와 파밍은 넣지 않는다.

완성된 게임은 다음 흐름을 실제로 제공해야 한다.

```text
타이틀
→ 거점
→ 탐험
→ 가시적 적 조우
→ 반응형 턴제 전투
→ 기술·무기·유물 성장
→ 성소 탐험
→ 수호자 전투
→ 세계 봉인 획득
→ 다음 지역 개방
→ 세 번 반복
→ 세계뿌리 심부
→ 다단계 최종 보스
→ 엔딩
→ 승리 화면
```

다음은 완성이 아니다.

- 메뉴만 존재하는 목업
- 전투 한 번만 가능한 데모
- 색칠된 사각형과 원이 최종 아트인 상태
- 적 턴에 플레이어 입력이 없는 일반적인 메뉴식 턴제
- 회피와 패링이 이름만 다르고 실제 역할이 같은 상태
- 빌드 시스템이 수치 증가만 제공하는 상태
- 최종 보스나 엔딩에 정상적으로 도달할 수 없는 상태
- 실제 실행하지 않은 테스트를 통과했다고 표시한 상태

범위 압박이 생기면 **콘텐츠 수보다 전투 완성도와 전체 진행 가능성**을 우선한다.

# 2. 독창성

현대 반응형 턴제 RPG의 다음 설계 원리를 참고한다.

- 턴제 의사결정과 실시간 반응 입력의 결합
- 적 턴의 회피·패링·점프
- 성공적인 방어가 행동력·반격·캐릭터 자원으로 연결되는 구조
- 공격 애니메이션과 동기화된 입력
- 적 스프라이트의 약점 직접 조준
- 붕괴 게이지와 버스트 타이밍
- 캐릭터마다 다른 고유 자원 순환
- 장비 패시브를 숙련해 별도 빌드 요소로 재사용하는 성장 방식

그러나 특정 상업 게임의 캐릭터, 명칭, 대사, 세계관, 적 디자인, UI 배치, 음악, 아이콘, 애니메이션 또는 아트 자산을 복제하지 않는다.

모든 고유명사와 세부 규칙은 이 게임만의 형태로 만든다.

---

# 3. 세계관과 진행

세계의 지형과 생명을 이어 주던 거대한 지하 생명체 **세계뿌리**가 오염되었다.

상처에서 자라난 **잔향가시**는 기억과 지형을 뒤섞고 생물을 변이시킨다.

세계뿌리를 안정시키던 세 개의 **세계 봉인**은 각각 타락한 성소에 묻혀 있다.

플레이어의 목적은 다음과 같다.

```text
거점을 떠난다
→ 세 지역의 오염을 조사한다
→ 각 성소의 수호자를 쓰러뜨린다
→ 세 세계 봉인을 회수한다
→ 세계뿌리 심부를 개방한다
→ 최종 수호자를 물리친다
→ 세계뿌리의 운명을 결정한다
```

긴 설명문보다 다음을 통해 서사를 전달한다.

- 환경 변화
- 벽화와 유적
- 버려진 야영지
- 짧은 동료 대화
- 보스 전후 장면
- 탐험 중 발견하는 기록

서사는 짧지만 시작, 전개, 결말이 명확해야 한다.

---

# 4. 월드와 탐험

고품질 2D RPG에 맞춰 **핵심 진행 경로는 직접 설계된 구조**로 만든다.

무제한 절차 생성은 필수가 아니다. 재플레이 변화를 넣고 싶다면 필수 진행을 흔들지 않는 범위에서만 시드 기반 변형을 사용한다.

## 주요 지역

1. **푸른 피난처** — 시작 거점과 튜토리얼
2. **재빛 초원** — 기본 전투와 방어 학습
3. **잠긴 폐허** — 상태 효과와 붕괴
4. **유리숲** — 약점 조준과 부위 파괴
5. **부서진 고원** — 복합 전투와 강적
6. **세계뿌리 심부** — 최종 구역

세 개의 성소는 서로 다른 지역과 연결한다.

## 필드 행동

플레이어는 다음을 할 수 있다.

- 4방향 또는 8방향 이동
- 달리기
- 상호작용
- 상자 열기
- 휴식 지점 활성화
- 동료와 대화
- 표지·벽화·유물 조사
- 비밀길 발견
- 화면에 보이는 적과 접촉해 전투 시작

필드에는 별도의 실시간 전투를 넣지 않는다. 탐험과 전용 턴제 전투를 분리해 두 개의 얕은 전투 시스템이 생기는 것을 막는다.

## 조우

- 강제 랜덤 인카운터를 사용하지 않는다.
- 적은 필드에 실제 스프라이트로 존재한다.
- 뒤에서 접근하면 작은 선제 이점을 줄 수 있다.
- 적에게 기습당하면 적이 작은 선제 이점을 얻을 수 있다.
- 일반 전투 진입과 복귀는 짧고 빠르게 처리한다.

## 탐험 보상

탐험 보상은 전투 선택지를 확장해야 한다.

- 새로운 무기
- 유물
- 기술 해금 재료
- 빌드 용량 증가
- 회복 아이템
- 숨겨진 강적
- 지름길
- 짧은 서사

의미 없는 수집품을 대량으로 배치하지 않는다.

# 5. 파티

플레이어 캐릭터는 네 명이다.

- 전투에는 세 명이 참가한다.
- 한 명은 대기한다.
- 전투 전 또는 휴식 지점에서 교체할 수 있다.
- 각 캐릭터는 최소 8개의 기술을 배우고 그중 6개를 장착한다.
- 각 캐릭터는 최소 2개의 플레이 방식을 바꾸는 무기를 가진다.
- 단순한 전사·마법사·힐러 색상 변경이 아니라 서로 다른 자원 순환을 가진다.

## 카엘 — 자세 순환

세 가지 검술 자세를 사용한다.

- **수호**: 받는 피해와 실수 위험 감소, 반격 강화
- **공세**: 공격과 붕괴 피해 강화
- **흐름**: 행동력 효율과 연속 공격 강화

기술이 자세를 바꾸거나 현재 자세에 따라 효과가 달라진다.

완벽 패링은 자세 전환 또는 자세 보너스와 연결한다.

## 미라 — 원소 인장

세 원소를 사용한다.

- 화염
- 조류
- 폭풍

마법 사용 후 원소 인장이 남고 다음 기술이 특정 조합을 소비한다.

예:

```text
화염 + 화염 → 강한 화상
조류 + 폭풍 → 연쇄 공격
화염 + 조류 → 증기 폭발 + 붕괴
세 원소 모두 → 고비용 필살기
```

현재 피해보다 **다음 행동을 어떤 상태로 만들지**가 중요해야 한다.

## 세라 — 표식과 정밀 조준

적 또는 신체 부위에 표식을 남긴다.

- 균열 표식
- 추적 표식
- 메아리 표식

정밀 조준으로 실제 약점을 맞히면 표식이 강화되거나 폭발한다.

약점 공격과 파티 연계를 가장 적극적으로 사용하는 캐릭터다.

## 오린 — 충전과 소비

다음으로 충전을 획득한다.

- 기본 공격
- 공격 타이밍 성공
- 동료 반격
- 붕괴한 적 공격

충전을 소비해 다음을 사용한다.

- 고위력 포격
- 파티 보호막
- 강한 붕괴 공격
- 비상 행동력 지원

충전 상한을 두어 즉시 사용할지 큰 버스트를 위해 저장할지 선택하게 한다.

# 6. 전투 기본 구조

전투는 측면 또는 약한 유사 원근의 전용 2D 화면에서 진행한다.

- 아군은 왼쪽, 적은 오른쪽을 기본으로 한다.
- 행동 순서를 보여 주는 타임라인을 표시한다.
- 지역별 전투 배경을 사용한다.
- 캐릭터와 적은 대기 애니메이션을 가진다.
- 공격은 준비 → 충돌 → 회복이 보이게 한다.

핵심 순환:

```text
턴 순서 확인
→ 행동력·고유 자원 확인
→ 기술과 대상 선택
→ 공격 타이밍 수행
→ 피해·상태·붕괴 처리
→ 적의 예고 동작
→ 회피·패링·점프 대응
→ 행동력·반격·공명 보상
→ 다음 턴 선택 변화
```

실시간 입력은 별도의 QTE 장식이 아니라 **다음 전략적 선택을 바꾸는 자원 생성 방식**이어야 한다.

---

# 7. 행동력(AP)

행동력은 스킬 사용의 핵심 자원이다.

권장 시작값:

- 최대 행동력: 10
- 전투 시작: 3
- 자기 턴 시작 기본 회복: 1
- 기본 공격: 행동력 생성
- 완벽 패링: 행동력 또는 캐릭터 자원 생성

기술은 저비용 준비기, 주력기, 고비용 보상기로 나눈다.

행동력 때문에 다음 선택이 실제로 갈려야 한다.

- 지금 사용
- 다음 턴을 위해 저장
- 기본 공격으로 생성
- 붕괴 준비
- 동료 지원
- 회복

무한 행동력 루프를 허용하지 않는다.

---

# 8. 공격 타이밍

여러 공격 기술은 애니메이션과 동기화된 입력을 가진다.

사용 가능한 패턴:

- 단일 충돌 순간 입력
- 여러 박자의 연속 입력
- 누르고 적정 시점에 놓기
- 3~5회의 짧은 리듬 입력

결과:

- **실패**: 약화된 효과
- **성공**: 정상 효과
- **완벽**: 추가 피해, 붕괴, 행동력 또는 고유 자원 보너스

일반 기술은 타이밍 실패 때문에 턴 전체가 사라지지 않게 한다.

모든 기술에 같은 막대 UI를 붙이지 말고 실제 공격 동작과 맞춘다.

# 9. 적 턴의 능동 방어

직접 공격은 플레이어가 반응할 수 있는 시각·음향 예고를 제공한다.

지속 피해나 이미 걸린 상태 효과 같은 비직접 피해는 별도 반응 입력을 요구하지 않아도 된다.

## 회피

- 가장 넓고 안전한 판정
- 성공 시 피해 회피
- 자원 보상은 작음
- 처음 보는 패턴에 유리

## 패링

- 회피보다 좁은 판정
- 성공 시 해당 타격 무효화
- 행동력 또는 고유 자원 획득
- 한 연속 공격의 모든 타격을 패링하면 전용 **반격** 발동

반격은 다음을 가진다.

- 별도 애니메이션
- 강한 타격감
- 높은 붕괴 기여
- 명확한 보상

## 점프 대응

다음과 같은 지면 공격에 사용한다.

- 충격파
- 낮은 쓸기
- 지면 균열
- 파도형 공격

필요한 공격은 자세, 실루엣, 지면 효과와 소리로 구분한다.

점프 대응은 기본 이동키와 충돌하지 않는 별도 입력으로 지정하고 키 재설정을 지원한다.

## 연속 공격

각 타격을 개별 판정한다.

```text
베기
→ 짧은 정지
→ 빠른 2연타
→ 지연된 강타
```

공격 간격은 항상 일정하지 않아도 되지만 학습 가능하고 공정해야 한다.

---

# 10. 반응 판정 구현

반응 입력은 프레임 수가 아니라 게임 시간으로 계산한다.

- 엔진의 고해상도 시간 또는 브라우저 고해상도 타이머 사용
- 명시적 상태 머신 사용
- 짧은 입력 버퍼 제공
- 판정 폭은 데이터로 관리
- 프레임 드롭이나 고주사율 환경에서도 결과가 일관되어야 함

정확한 밀리초 값은 애니메이션과 실제 플레이테스트를 통해 난이도별로 조정한다.

코드 안에 여러 곳으로 흩어진 매직 넘버를 두지 않는다.

# 11. 2D 정밀 조준

3D 자유 카메라를 흉내 내지 않는다.

적 스프라이트 자체에 약점 영역을 정의하고 직접 조준한다.

정밀 조준 시:

1. 현재 행동 해결을 정지한다.
2. 필요하면 적을 정수 배율로 확대한다.
3. 조준점을 표시한다.
4. 마우스·키보드·게임패드로 움직인다.
5. 실제 스프라이트의 약점 영역을 겨냥한다.
6. 선택 지점을 공격한다.

약점 예:

- 빛나는 눈
- 수정 핵
- 갑옷 이음새
- 방패 고정쇠
- 무기를 든 손
- 충전 기관
- 기생체

명중 효과 예:

- 추가 피해
- 공격 패턴 봉쇄
- 갑옷 제거
- 충전 취소
- 붕괴 증가
- 다음 약점 노출
- 보스 패턴 변화

`[머리] [팔] [핵]` 같은 메뉴 선택으로 대체하지 않는다.

---

# 12. 붕괴

적은 체력과 별도의 붕괴 게이지를 가진다.

- 일반 피해와 붕괴 피해를 구분한다.
- 게이지를 채운 뒤 붕괴 가능 기술로 발동한다.
- 붕괴는 적의 다음 행동을 취소하거나 늦춘다.
- 일정 시간 또는 행동 수 동안 받는 피해가 증가한다.
- 전용 비틀거림 애니메이션을 사용한다.

보스의 붕괴는 단순한 두 번째 체력바가 아니라 **강력한 패턴을 끊고 공격 기회를 만드는 전술 목표**여야 한다.

---

# 13. 공명

파티 공유 자원 **공명**을 사용한다.

다음 행동으로 공명을 얻는다.

- 완벽 공격 타이밍
- 연속 공격 완전 패링
- 약점 명중
- 붕괴 발동
- 특정 상태 연계

3칸 게이지로 운용한다.

- 1칸: 비상 개입 또는 구조 기술
- 2칸: 캐릭터 고유 강력기
- 3칸: 파티 연계기

공명 기술은 전용 애니메이션과 강한 피드백을 가진다.

---

# 14. 상태 효과

종류는 적게 유지하되 서로 연결한다.

- **화상**: 지속 피해
- **표식**: 조건부 다음 공격 강화
- **노출**: 약점 피해 증가
- **수호**: 받는 피해 감소
- **보호막**: 고정량 피해 흡수
- **둔화**: 타임라인 뒤로 이동
- **가속**: 타임라인 앞으로 이동
- **취약**: 붕괴 피해 증가
- **혼미**: 다음 공격 약화

각 상태는 최소 하나 이상의 기술, 무기, 유물, 캐릭터 자원 또는 적 기믹과 상호작용해야 한다.

# 15. 성장과 빌드

## 기술

- 캐릭터당 최소 8개 습득
- 전투에는 6개 장착
- 저비용 생성기, 준비기, 주력기, 붕괴기, 방어·지원, 고비용 보상기를 포함
- 같은 기술에 색만 바꾼 복제품을 만들지 않음

## 무기

캐릭터당 최소 2개를 제공한다.

단순 공격력 상위 호환이 아니라 플레이 스타일을 바꾼다.

예:

- 패링 중심 / 붕괴 중심
- 원소 생성 중심 / 소비 중심
- 약점 중심 / 표식 중심
- 빠른 충전 / 높은 최대 충전

## 유물

각 캐릭터는 유물 3개를 장착한다.

유물은 능력치와 고유 패시브를 제공한다.

최소 12개의 의미 있는 유물을 만든다.

예:

- 완벽 패링 시 임시 공격 강화
- 약점 명중 시 추가 붕괴
- 전투 시작 체력이 가득 차면 행동력 보너스
- 반격이 표식 부여
- 위기 상태의 동료를 회복하면 보호막 부여

## 유물 숙련과 메아리

유물을 실제 전투에서 사용하면 숙련도가 오른다.

숙련 완료 후 해당 패시브는 **메아리**로 등록되어 유물을 벗어도 별도로 장착할 수 있다.

메아리는 제한된 **통찰력**을 소비한다.

최종 빌드:

```text
무기
+ 장착 기술 6개
+ 유물 3개
+ 통찰력 한도 내 메아리
+ 파티 조합
+ 플레이어의 반응 숙련
```

숙련 진행도와 해금 순간을 명확하게 보여 준다.

## 능력치

복잡도를 억제하기 위해 다음 정도로 제한한다.

- 생명력
- 공격력
- 방어력
- 민첩
- 집중

레벨업은 기본 성장만 제공하고 큰 플레이 차이는 기술, 무기, 유물, 메아리에서 만든다.

반복 사냥을 요구하지 않는다.

# 20. 코드 기반 2D 픽셀아트

게임의 핵심 비주얼은 **이미지 생성 모델이나 외부 이미지 제작 도구에 의존하지 않고 코드와 데이터로 직접 관리·생성한다.**

아트의 원본(source of truth)은 PNG 파일이 아니라 다음과 같은 코드/데이터여야 한다.

- 팔레트 정의
- 픽셀 클러스터와 형태 정의
- 캐릭터 신체 비율
- 장비·의상 레이어
- 포즈 데이터
- 애니메이션 프레임 정의
- 타일 규칙
- 장식 배치 규칙
- 이펙트 패턴
- 스프라이트 앵커와 약점 좌표

빌드 또는 개발 스크립트가 이 데이터를 읽어 실제 게임용 스프라이트시트, 아틀라스, 타일셋 또는 런타임 텍스처를 생성한다.

생성된 PNG/JSON은 **빌드 산출물 또는 캐시**로 취급할 수 있지만, 이를 수동으로 수정하는 방식이 핵심 제작 흐름이 되어서는 안 된다.

## 코드 생성 원칙

허용되는 방식의 예:

- TypeScript/JavaScript 픽셀 버퍼 생성기
- Canvas 2D를 이용한 정수 좌표 래스터 드로잉
- 색상 인덱스 배열을 실제 픽셀로 변환
- 작은 픽셀 패턴을 조합하는 타일 생성기
- 캐릭터 신체 파츠와 포즈 정의를 조합하는 스프라이트 빌더
- 프레임별 보정 픽셀을 추가하는 애니메이션 생성기
- Phaser를 사용한다면 CanvasTexture, DynamicTexture, TextureManager 또는 생성된 스프라이트시트/아틀라스

단, **코드로 그린다는 이유로 단순 사각형과 원을 조립한 개발용 그림을 최종 아트로 인정하지 않는다.**

최종 결과는 실제 픽셀 아티스트가 픽셀 단위로 정리한 것처럼 보여야 한다.

다음을 피한다.

- 단순 기하 도형만 조합한 사람 모양
- 자동 회전한 저해상도 팔·다리
- 벡터 도형을 축소해 도트처럼 보이게 한 결과
- 매 프레임 같은 몸통을 이동만 시킨 인형극 애니메이션
- 무작위 픽셀 노이즈
- 과도한 디더링
- 흐린 안티앨리어싱

필요하면 각 포즈마다 파츠 위치를 다시 정의하고, 실루엣과 관절에 **프레임별 픽셀 보정**을 넣는다.

---

## 20.1 픽셀 렌더링 기준

권장 논리 해상도는 다음 중 하나를 사용한다.

- 384×216
- 480×270
- 또는 같은 목적에 맞는 유사한 16:9 저해상도

320×180도 가능하지만 전투 스프라이트와 UI가 지나치게 좁아지면 더 높은 논리 해상도를 선택한다.

렌더링 규칙:

- 모든 핵심 픽셀 좌표는 정수 좌표를 사용한다.
- 스프라이트는 기본적으로 정수 배율로 표시한다.
- 최근접 보간을 사용한다.
- 런타임에서 임의의 비정수 확대·축소를 피한다.
- 픽셀 캐릭터에 흐린 모션 블러를 사용하지 않는다.
- 픽셀 경계를 보존한다.

Phaser를 사용할 경우 `pixelArt` 또는 동등한 nearest-neighbor 설정을 활성화한다.

---

## 20.2 팔레트와 셰이딩

전역 팔레트를 먼저 정의하고 각 캐릭터와 지역은 그 안에서 제한된 램프를 사용한다.

권장:

- 캐릭터 하나당 핵심 색상 약 12~24색
- 주요 재질당 3~5단계 명암 램프
- 이펙트는 별도 강조색 허용
- 공통 광원 방향 유지
- 선택적 1픽셀 외곽선
- 내부선은 외곽선보다 약하게 사용

다음을 금지한다.

- 자동 그라디언트
- 재질 구분 없는 단순 밝기 변화
- 모든 경계에 검은색 한 줄을 두르는 기계적 외곽선
- 픽셀 하나짜리 잡음으로 질감을 표현하는 방식

큰 면은 **읽히는 픽셀 클러스터**를 만든다.

머리카락, 천, 금속, 가죽, 돌, 뿌리, 물은 서로 다른 명암 패턴과 가장자리 패턴을 가져야 한다.

---

## 20.3 필드 캐릭터 비율

필드 탐험에서는 가독성과 이동 공간을 우선한다.

플레이어 필드 스프라이트 기본값:

```text
프레임: 24×32 또는 32×40
실제 신체 높이: 약 24~30px
비율: 약 3~3.5등신
```

필드에서는 머리를 약간 크게 만들어 방향과 캐릭터 구분을 쉽게 한다.

그러나 전투용 스프라이트를 단순 확대해서 사용하지 않는다.

필드와 전투는 같은 캐릭터 디자인을 공유하되 서로 다른 비율과 프레임을 가진 별도 표현으로 만든다.

---

## 20.4 플레이어 전투 스프라이트 표준

모든 플레이어 캐릭터는 **팔·다리·무기·몸통 방향과 공격 타이밍이 명확히 읽히는 인간형 비율**을 사용한다.

기본 표준:

```text
기본 프레임: 48×64
필요 시: 56×72 또는 64×72
실제 캐릭터 높이: 약 44~56px
권장 신체 비율: 약 4.5~5.5등신
```

극단적인 2~3등신 전투 캐릭터는 피한다.

이유는 다음 동작이 한눈에 구분되어야 하기 때문이다.

- 검을 뒤로 당기는 준비 자세
- 공격 팔의 전진
- 앞발과 뒷발의 체중 이동
- 패링 시 무기 방향
- 회피 방향
- 점프 자세
- 피격 시 상체 반동
- 반격의 시작과 끝

권장 신체 픽셀 범위는 절대 규칙이 아니라 설계 기준으로 사용한다.

```text
머리 높이: 약 9~12px
어깨 폭: 약 14~19px
몸통: 약 14~18px
골반 영역: 약 4~7px
다리: 약 18~23px
손·발 덩어리: 최소 3px 이상의 읽히는 형태
```

머리카락이나 장식 때문에 실제 외곽 높이가 달라져도 **눈, 어깨, 골반, 발 위치의 기준선**은 캐릭터 간 최대한 일관되게 유지한다.

모든 플레이어 전투 스프라이트는 공통 바닥 앵커를 사용한다.

권장:

```text
originX = 0.5
originY = 1.0
```

또는 엔진에 맞는 동등한 발 기준 앵커를 사용한다.

프레임마다 발 위치가 흔들리는 현상을 금지한다.

---

## 20.5 무기와 공격 범위

긴 검, 창, 지팡이, 총기처럼 신체 밖으로 크게 뻗는 무기는 캐릭터 본체를 억지로 작은 프레임 안에 압축하지 않는다.

필요하면:

- 64×64
- 64×72
- 80×72

같은 넓은 프레임을 사용한다.

무기 궤적이 프레임 가장자리에서 잘리면 안 된다.

공격 판정과 시각적 접촉점은 실제 무기 끝 또는 효과 위치와 맞아야 한다.

---

## 20.6 적 캐릭터 비율

적은 종류에 따라 크기를 달리하되, 공격 준비와 타격점이 읽혀야 한다.

### 소형 적

```text
프레임: 32×32 ~ 40×40
실제 높이: 최소 약 24px
플레이어 대비 시각 높이: 약 0.5~0.75배
```

작더라도 공격 기관과 이동 방향이 읽혀야 한다.

### 인간형·중형 적

```text
프레임: 48×64 ~ 56×72
권장 비율: 약 4~6등신
플레이어 대비 시각 높이: 약 0.9~1.25배
```

플레이어와 직접 검을 맞대거나 패링해야 하는 적은 이 범위를 기본으로 한다.

### 대형 적

```text
프레임: 약 72×80 ~ 80×96
플레이어 대비 시각 높이: 약 1.3~1.7배
```

팔, 머리, 핵, 앞발 같은 공격 부위가 별도로 읽혀야 한다.

### 보스

```text
권장 프레임: 96×96 ~ 128×112
플레이어 대비 시각 높이: 약 1.8~2.4배
```

하나의 거대한 고정 이미지 대신 필요하면 다음처럼 분리한다.

```text
몸통
팔
무기
날개 또는 부속 기관
약점 부위
이펙트
```

단, 파츠 분리는 애니메이션 제작을 쉽게 하기 위한 내부 구조일 뿐 최종 결과가 종이인형처럼 보이면 안 된다.

대형 보스는 전투 공간 높이의 약 40~55% 안에서 실루엣이 읽히도록 한다.

UI와 겹쳐 공격 예고가 가려지지 않아야 한다.

---

## 20.7 적 크기와 반응 타이밍의 관계

적 크기와 관계없이 방어 타이밍은 **실제 애니메이션의 충돌 프레임**에 맞춘다.

예:

```text
무기 뒤로 당김
→ 전진
→ 패링 가능 구간
→ 실제 접촉 프레임
→ 후속 동작
→ 회복
```

거대한 적이라고 공격이 자동으로 느려지는 것도 아니고, 작은 적이라고 모든 공격이 빠른 것도 아니다.

실루엣과 애니메이션을 통해 속도를 예측할 수 있게 만든다.

---

## 20.8 전투 애니메이션 프레임 기준

프레임 수보다 **준비 → 충돌 → 회복**의 구분이 더 중요하다.

권장 시작점:

```text
대기             4~6프레임
기본 공격         5~8프레임
복합 기술         6~12프레임 이상
회피             4~6프레임
패링             3~5프레임
반격             6~10프레임
점프 대응         4~7프레임
피격             2~4프레임
붕괴/스태거       3~6프레임
승리             4~8프레임
패배             6~10프레임
```

적 공격은 최소한 다음 상태를 시각적으로 구분한다.

```text
anticipation
attack
contact
recovery
```

패링을 요구하는 공격은 **contact 프레임이 명확해야 한다.**

멀티히트 공격은 각 타격의 실제 접촉 프레임을 개별적으로 정의한다.

프레임 배열과 실제 판정 타임라인은 같은 데이터에서 파생되거나 명시적으로 연결한다.

---

## 20.9 포즈 생성 방식

몸을 단순 회전시키는 방식보다 **프레임별 포즈 블루프린트**를 사용한다.

예:

```text
head:      x, y, variant
body:      x, y, pose
armFront:  joint positions / sprite variant
armBack:   joint positions / sprite variant
legFront:  pose
legBack:   pose
weapon:    variant / attachment point
cape:      variant
correctionPixels: [...]
```

각 포즈에서 필요하면 픽셀 클러스터를 직접 다시 그린다.

낮은 해상도에서 팔·다리를 임의 각도로 회전한 뒤 자동 보간하지 않는다.

특히 다음 프레임에는 수작업 수준의 픽셀 보정을 적용한다.

- 공격 최고점
- 실제 접촉 프레임
- 패링 접촉 프레임
- 피격 프레임
- 착지
- 보스 약점 노출

---

## 20.10 실루엣 규칙

모든 플레이어 캐릭터는 색을 제거하고 단색 실루엣으로 보더라도 구분 가능해야 한다.

캐릭터 차별화 수단:

- 머리 형태
- 어깨 폭
- 코트·망토 길이
- 무기 길이
- 자세
- 팔의 기본 위치
- 다리 간격
- 장식의 방향

적도 마찬가지다.

같은 기본 사람 스프라이트에 색만 바꿔 적 종류를 늘리지 않는다.

---

## 20.11 약점과 정밀 조준용 픽셀 기준

정밀 조준 대상은 실제 스프라이트에 존재해야 한다.

예:

- 눈
- 노출된 핵
- 손의 무기
- 갑옷 연결부
- 수정 기관

시각적 약점은 최소한 몇 픽셀 이상의 읽히는 덩어리를 가진다.

실제 입력용 히트 영역은 가독성을 위해 시각적 픽셀보다 약간 넓게 잡을 수 있지만, **눈에 보이는 위치와 판정 위치가 어긋나면 안 된다.**

약점 좌표는 캐릭터 프레임 데이터와 함께 관리한다.

---

## 20.12 이펙트 레이어

다음을 캐릭터 본체와 별도 레이어로 관리한다.

- 베기 궤적
- 마법광
- 패링 불꽃
- 총구 화염
- 붕괴 파편
- 상태 효과
- 그림자
- 피격 플래시

이펙트가 캐릭터의 팔·무기·적 공격 자세를 가리지 않게 한다.

반응 입력 구간에서는 불필요한 이펙트를 줄여 적 공격 실루엣을 최우선으로 보존한다.

---

## 20.13 지형과 배경 코드 생성

기본 지형 그리드는 16×16 픽셀을 권장한다.

지형 생성 코드는 최소 다음 변형을 제공한다.

- 내부 타일
- 가장자리
- 안쪽 모서리
- 바깥쪽 모서리
- 전환 타일
- 불규칙 변형
- 장식 오버레이

타일 하나를 색만 바꿔 모든 지역에 재사용하지 않는다.

코드 기반 생성 시에도 숲, 돌, 습지, 폐허, 오염 지역은 서로 다른 픽셀 클러스터 규칙과 재질 램프를 가져야 한다.

사각형 바이옴 경계와 눈에 띄는 반복 패턴을 피한다.

---

## 20.14 코드 기반 아트 파이프라인

프로젝트에 명확한 아트 생성 파이프라인을 둔다.

예시 구조:

```text
src/art/
  palettes/
  primitives/
  characters/
  enemies/
  tiles/
  props/
  effects/
  poses/
  animationSpecs/

tools/artgen/
  generateCharacters.ts
  generateEnemies.ts
  generateTiles.ts
  generateEffects.ts
  buildAtlas.ts
  validateArt.ts

public/generated/
  sprites/
  tiles/
  atlases/
  manifests/
```

프로젝트 구조에 따라 이름은 바꿔도 된다.

핵심은 다음이다.

```text
코드/데이터 수정
→ art generator 실행
→ spritesheet/atlas 생성
→ validator 실행
→ 게임에서 로드
```

생성 산출물에는 가능한 범위에서 메타데이터를 함께 기록한다.

```text
frame size
frame names
animation names
origin
feet anchor
weapon attachment
weak points
hitbox hints
palette id
```

## 20.15 런타임 생성과 빌드타임 생성

둘 다 가능하다.

### 기본 권장

캐릭터·적·타일처럼 반복 사용되는 핵심 자산은 **빌드타임에 생성해 스프라이트시트/아틀라스로 고정**한다.

장점:

- 재현 가능
- 디버깅 쉬움
- 프레임별 비교 쉬움
- 런타임 비용 감소
- 시각 회귀 테스트 용이

### 런타임 생성이 적합한 것

- 팔레트 스왑
- 간단한 파티클
- 일회성 마법 효과
- 절차 장식
- 디버그 표현

모든 프레임을 매번 런타임에서 새로 그릴 필요는 없다.

---

## 20.16 코드 아트 검증

아트 생성 후 자동 검사 가능한 항목을 검증한다.

- 프레임 크기가 사양과 일치하는가
- 필요한 애니메이션 프레임이 존재하는가
- 투명 배경이 유지되는가
- 캐릭터 발 앵커가 프레임마다 튀지 않는가
- 허용되지 않은 팔레트 색이 섞이지 않았는가
- 약점 좌표가 프레임 밖으로 나가지 않는가
- 스프라이트 키와 매니페스트가 일치하는가
- 애니메이션 이름 누락이 없는가
- 비정상적으로 빈 프레임이 없는가

개발 중에는 캐릭터별 **contact sheet**를 코드로 자동 생성한다.

한 장에서 다음을 비교할 수 있게 한다.

```text
idle
attack anticipation
attack contact
parry
counter
hurt
break
victory / defeat
```

이 접촉 시트를 실제로 확인해 관절 파손, 프레임 흔들림, 잘린 무기, 불명확한 공격 방향을 수정한다.

---

## 20.17 고품질 픽셀아트 완료 기준

다음 조건을 모두 만족해야 한다.

- 이미지 생성 AI를 핵심 게임 비주얼 제작에 사용하지 않는다.
- 플레이어 4명의 픽셀 원본이 코드와 데이터로 재생성 가능하다.
- 모든 일반 적과 보스 역시 같은 파이프라인으로 재생성 가능하다.
- 전투 스프라이트가 필드 스프라이트의 단순 확대본이 아니다.
- 인간형 전투 캐릭터의 팔·다리·몸통이 공격 중 명확히 구분된다.
- 플레이어 네 명의 실루엣이 서로 구분된다.
- 적 아키타입이 색상 변경만으로 구분되지 않는다.
- 패링할 공격의 실제 접촉 프레임이 눈으로 읽힌다.
- 대형 적과 보스의 공격 부위가 명확하다.
- 모든 핵심 스프라이트가 최근접 보간으로 선명하다.
- 무기와 이펙트가 프레임 밖에서 잘리지 않는다.
- 자동 생성 결과에 디버그 도형이나 임시 사각형이 남지 않는다.

## 최종 아트 금지

- 이미지 생성 모델에 최종 스프라이트 제작을 맡기는 방식
- 외부에서 생성한 그림을 자동 픽셀화해 핵심 캐릭터로 사용하는 방식
- 색칠된 사각형 캐릭터
- 이모지
- 디버그 아이콘
- 사진 텍스처
- 흐린 업스케일
- 서로 맞지 않는 픽셀 밀도
- 일반 웹 UI용 벡터 그림을 그대로 붙인 화면
- 랜덤 노이즈로 만든 가짜 디테일
- 같은 캐릭터 베이스를 팔레트만 바꾼 적 군단

# 22. 한국어 출력

게임 내 플레이어 노출 텍스트는 모두 자연스러운 한국어로 작성한다.

포함 범위:

- 타이틀과 메뉴
- 튜토리얼
- 대화와 내레이션
- 목표
- 기술·무기·유물·메아리·아이템 이름과 설명
- 상태 효과
- 전투 메시지
- 적 조사
- 설정
- 저장·불러오기
- 오류·경고·확인 문구
- 패배·승리·엔딩·크레디트
- 조작 안내

영어 임시 문구, 번역 키, `TODO`, `Lorem ipsum`이 사용자 화면에 노출되지 않게 한다.

## 용어

- Action Point → **행동력(AP)**
- Break → **붕괴**
- Counter → **반격**
- Precision Aim → **정밀 조준**
- Resonance → **공명**
- Relic → **유물**
- Echo → **메아리**
- Insight → **통찰력**
- Perfect Parry → **완벽 패링**

표현은 짧고 자연스러운 한국어 게임 문장으로 쓴다.

예:

```text
나쁜 표현: Dodge Success! AP +1
좋은 표현: 회피 성공

나쁜 표현: Perfect Parry! AP +1
좋은 표현: 완벽 패링 — 행동력 +1

나쁜 표현: The enemy is broken.
좋은 표현: 적이 붕괴했다.
```

사용자 노출 문자열은 중앙 로케일 데이터나 이에 준하는 구조로 관리한다.

한글 폰트는 외부 네트워크가 없어도 표시 가능한 폴백을 둔다.

긴 한국어 설명, 작은 창, 높은 UI 배율에서도 버튼과 텍스트가 잘리지 않게 한다.

# 25. 기술 선택

목표 플랫폼은 **현대 데스크톱 브라우저**다.

구현 기술은 현재 프로젝트와 완성 가능성을 기준으로 선택한다.

적합한 선택 예:

- Phaser
- PixiJS 기반 구조
- 다른 안정적인 2D 웹 게임 프레임워크
- 필요한 기능을 충분히 제공하는 기존 프로젝트 스택

Phaser는 좋은 기본 선택이지만 필수는 아니다.

프레임워크를 바꾸는 것 자체가 목적이 되어서는 안 된다. 다음 기능을 가장 안정적으로 제공하는 구성을 선택한다.

- 2D 렌더링
- 입력
- 애니메이션
- 씬·상태 관리
- 오디오
- 자산 로딩
- 픽셀 선명도
- 저장
- 테스트 가능성

TypeScript를 기본 언어로 사용하되 기존 프로젝트에 명확한 이유가 있으면 호환 가능한 언어 구성을 유지해도 된다.

백엔드는 핵심 게임에 필요하지 않다.

# 32. 전투 길이와 밸런스

목표:

- 일반 전투: 2~5 플레이어 라운드
- 정예: 4~7 라운드
- 수호자: 5~10 라운드

패링, 약점, 붕괴, 빌드 시너지를 잘 활용하면 전투 시간이 눈에 띄게 줄어야 한다.

회피와 패링의 역할을 분명히 유지한다.

```text
회피 = 안전하고 쉬움, 보상 적음
패링 = 어렵고 위험함, 자원과 반격 보상 큼
```

다음과 같은 퇴행적 루프를 막는다.

- 행동력 무한 생성
- 영구 기절
- 무한 회복
- 보스가 행동하지 못하는 영구 제어

그러나 강한 빌드를 완성했을 때 확실히 강해지는 재미까지 제거하지 않는다.

# 35. 최종 완료 게이트

다음이 모두 사실일 때만 완료로 간주한다.

- 게임을 실제로 실행할 수 있다.
- 새 게임부터 엔딩까지 정상 진행 가능하다.
- 일반 전투와 보스 전투가 실제 규칙으로 작동한다.
- 회피·패링·반격·점프 대응이 서로 다른 역할을 가진다.
- 공격 타이밍이 전투 결과에 영향을 준다.
- 붕괴가 전술적 공격 기회를 만든다.
- 네 캐릭터의 운영 방식이 체감상 다르다.
- 유물과 메아리가 빌드를 실제로 바꾼다.
- 픽셀아트가 코드/데이터 원본에서 재생성 가능하고, 흐리지 않으며 플레이스홀더가 남지 않는다.
- 플레이어·일반 적·보스의 전투 비율과 프레임 크기가 위 아트 규격을 따르고 공격·패링·피격 동작이 명확히 읽힌다.
- 모든 사용자 노출 텍스트가 한국어다.
- 저장 후 다시 실행해 진행을 이어갈 수 있다.
- 최종 보스를 정상적으로 쓰러뜨릴 수 있다.
- 엔딩과 승리 화면이 존재한다.
- 실제 실행한 검증 결과와 남은 한계를 구분해 보고한다.

완성 시 다음을 한국어로 간결하게 정리한다.

1. 실행 방법
2. 조작법
3. 구현된 핵심 시스템
4. 실제 수행한 테스트와 결과
5. 주요 구조
6. 남은 제한 사항이 있다면 그 내용

소스 전체를 채팅에 덤프하는 대신 실제 프로젝트 파일을 완성한다.

이제 구현을 시작하고, 위 완료 게이트를 만족할 때까지 실제 실행·수정·검증을 이어간다.
